# SkoolMate: Next 50 Recommended Upgrades, Fixes, and Debugs

**Prepared:** 10 November 2026
**Purpose:** A practical next-work backlog based on the recent live walkthrough, reported school workflows, current repository evidence, and open items in the October usability audits.

This is a prioritized recommendation list, not a claim that every item is a confirmed production defect or that SkoolMate is legally compliant. Items marked **Verify** need a real school, isolated test data, or an external record before deciding whether implementation is needed. The November registration agreement is in the working tree and its acceptance table has been added to the live Supabase project; the application change itself has not been deployed.

## P0 — Trust, privacy, and release readiness

1. **Deploy the registration agreement safely.** Publish the School Agreement and consent-version capture only after reviewing the exact text, applying the included migration, and confirming both password and Google registration paths. **Done when:** test registrations create one versioned acceptance record and existing accounts remain unaffected.

2. **Replace the privacy mailto link with a tracked request workflow.** Store access, correction, objection, and deletion requests with a reference number, owner, status, due date, and resolution notes; restrict the queue to authorised privacy staff. **Done when:** a user can submit, receive a reference, and see a confirmation without the request becoming a school-wide support ticket.

3. **Publish a verified service-provider schedule.** Inventory active hosting, database, authentication, email, SMS/WhatsApp, analytics, monitoring, and payment providers; document what data each receives and its processing locations. **Done when:** the privacy notice links to an owner-approved, current list and transfer review.

4. **Approve a real retention and deletion schedule.** Map each record type to its school purpose, legal retention basis, active retention period, backup expiry, and deletion/return method. **Done when:** schools can see an approved schedule and a completed deletion request has verifiable evidence.

5. **Capture lawful-basis and child-data evidence at school level.** Define how schools record notices and permissions for learners and sensitive records; a registration checkbox alone does not evidence consent from parents or guardians. **Done when:** the school can identify the applicable basis, notice version, responsible staff member, and evidence for a learner record.

6. **Audit tenant boundaries across every service-role API.** Review routes that use Supabase service credentials for explicit session, role, school, and record ownership checks. **Done when:** automated cross-school attempts return 403/404 and cannot read or mutate another school’s records.

7. **Add regression coverage for self-scoped privacy exports.** Verify a parent, teacher, administrator, and student each receive only their own permitted export scope. **Done when:** fixtures prove no school-wide messages, unrelated learners, or another school’s data can appear in exports.

8. **Introduce a controlled legal-version update flow.** Material term or privacy changes should have a version, effective date, notice strategy, acceptance record where needed, and a way to identify schools that have not accepted. **Done when:** the system can report the accepted version per school and handle an update without silently treating old acceptance as new.

9. **Write and rehearse a personal-data incident runbook.** Specify triage, containment, evidence preservation, school contact, regulator assessment, and breach-notice decision ownership. **Done when:** a tabletop exercise records response owners and measured notification steps.

10. **Separate demo and live data paths.** Audit demo logins, sample dashboards, exports, offline queues, and mutation handlers for any path that can touch real school records. **Done when:** demo use is isolated, visibly labelled, and automated checks detect attempted live writes.

## P1 — Offline reliability and sign-in continuity

11. **Publish an honest offline capability matrix.** For every key page, state whether it works on first offline launch, after prior caching, or only online; distinguish queued changes from confirmed server writes. **Done when:** teachers can tell before school starts which tasks are safe without data.

12. **Remove the signed-in PWA landing/login flash.** Resolve the initial session before rendering public home or login content, then route to the saved in-app destination or dashboard. **Done when:** warm launches go directly to the intended page with no visible route flicker on a slow phone.

13. **Cache an offline app shell and last-used route.** Keep signed-in navigation, cached page assets, and safe read-only content available when the network drops; never expose a previous user’s page. **Done when:** reopening in airplane mode reaches a useful cached view instead of a generic offline error.

14. **Add a class roster pre-download action.** Let a teacher choose classes and a school-approved data subset to cache before the day starts, with storage size and last-updated time shown. **Done when:** attendance opens offline with the full selected roster after a cold app restart.

15. **Show a durable sync queue with per-record states.** Display pending, syncing, synced, needs-attention, and failed rows, plus last attempt and retry controls. **Done when:** a teacher can identify exactly which attendance or grade entries are still on the phone.

16. **Make sync retries idempotent.** Give offline writes stable operation IDs and reject duplicate replay after timeouts, app restarts, or repeated taps. **Done when:** fault-injection tests replay the same queue several times and create one server record per action.

17. **Add understandable conflict resolution.** Detect when an offline edit conflicts with a later server update; show the affected fields and let authorised staff resolve it with an audit trail. **Done when:** two-device edits do not silently overwrite each other.

18. **Treat offline payments as pending, never settled.** Preserve an offline payment intent/receipt draft, but label it pending sync until the server confirms and reconciliation succeeds. **Done when:** reports, parent balances, and printed receipts cannot mistake a local queue entry for money received.

19. **Scope and clear offline storage by account and school.** On sign-out, role switch, or school switch, remove or re-key private IndexedDB data and queued writes safely. **Done when:** shared-device tests show no prior account’s learner or financial records after the next login.

20. **Run field-grade offline tests on real Android phones.** Include cold start, airplane mode, weak 2G/3G, storage pressure, battery saver, clock skew, and reconnection after several hours. **Done when:** the supported workflows pass with a timestamped sync receipt and no lost or duplicate records.

## P1 — Calendar, events, and working timetable

21. **Choose event audience explicitly.** Support personal, selected staff, selected class, and whole-school audiences, with the audience visible in the create and edit forms. **Done when:** no new event silently becomes public to the whole school.

22. **Add an event owner and delegated editor.** Record the creator, responsible staff member, and who may edit or cancel the event. **Done when:** an administrator can assign an event and the responsible teacher can manage it without broader school-wide permissions.

23. **Enforce event visibility on the server.** Filter event reads, edits, and deletes by audience and role in APIs/RLS; hiding a card in the UI is not sufficient. **Done when:** direct URL/API attempts outside the audience are denied.

24. **Give calendar entries precise dates and times.** Support all-day events, start/end time, location, timezone, and term/holiday context without recurring date shifts. **Done when:** teacher and administrator views agree on the same local time on Android and desktop.

25. **Add recurring events with safe exceptions.** Let schools set weekly or termly repeats, skip holidays, edit one occurrence or the series, and retain change history. **Done when:** editing one event does not unexpectedly rewrite the full term calendar.

26. **Notify the selected audience with delivery status.** Send in-app notices and optional push/SMS reminders according to role preferences; show queued, delivered, failed, and retried states. **Done when:** only intended recipients receive a reminder and failed delivery can be safely retried.

27. **Import timetable data in bulk from a spreadsheet.** Provide a downloadable template and preview mapping for days, periods, classes, subjects, rooms, and teachers. **Done when:** a school can validate rows and resolve errors before any timetable is saved.

28. **Prototype timetable-photo import with human review.** Let a school upload a timetable image, extract candidate rows, and correct OCR mistakes in a preview grid before saving. **Done when:** no OCR result is published without explicit review and clash validation.

29. **Make timetable editing and clash checks real.** Validate teacher, class, room, and period collisions while editing; explain the conflicting entries and suggest available slots. **Done when:** invalid schedules cannot be published accidentally.

30. **Deliver teacher-specific timetable reminders.** Notify each teacher of their own next class, time, room, and change/cancellation; allow quiet hours and notification preferences. **Done when:** a teacher receives only assigned schedule changes and can open the relevant timetable entry.

## P1 — Report cards and academic accuracy

31. **Move report-card settings into the report-card workflow.** Put grading basis, assessment components, term selection, and print layout next to report generation, with a short preview. **Done when:** teachers do not need to leave the report-card page to configure a report run.

32. **Support multiple school assessment models.** Configure CBC/competency, numerical, midterm, end-term, holiday, Saturday, and school-defined assessments without assuming a single universal weighting. **Done when:** each model saves a versioned configuration and preview calculations match that configuration.

33. **Show completeness before generating official reports.** Identify missing marks, maxima, teacher comments, student subjects, and signatures; distinguish zero from missing. **Done when:** incomplete reports are visibly provisional and cannot be ranked or published as final.

34. **Add teacher comments and signature workflow.** Collect subject-teacher and class-teacher comments/initials, then route reports for headteacher review and approval. **Done when:** each printed report shows who entered and approved each section, with date and audit trail.

35. **Offer selective and bulk printing.** Print one pupil, a selected class, a midterm batch, or a full term; include a print queue/progress indicator and recoverable PDF output. **Done when:** large classes can be generated without browser timeouts and page counts reconcile.

36. **Reconcile report calculations across screens and exports.** Compare grade entry, reports list, API, CSV/PDF, and printed totals using the same per-student denominator and missing-data rules. **Done when:** all representations match against agreed primary, secondary, CBC, and custom fixtures.

37. **Version report templates by school and academic period.** Preserve historical report layouts and grading configuration when a school changes its current template. **Done when:** reprinting an old term uses that term’s saved configuration rather than today’s settings.

38. **Verify curriculum and regulatory templates with authoritative sources.** Treat local reports and drafts as guidance until current NCDC/UNEB/MoES requirements are confirmed; track the source and review date in each template. **Done when:** schools can distinguish an officially accepted format from a SkoolMate convenience template.

## P2 — Parent, mobile, dashboard, and Owly experience

39. **Refresh the parent portal within SkoolMate’s design system.** Improve hierarchy, spacing, contrast, and readable mobile cards while keeping familiar SkoolMate components and navigation. **Done when:** parents complete common tasks on a small phone in moderated usability sessions.

40. **Make the parent home page action-first.** Put today’s attendance, latest result, fee balance, notices, and school contact in a clear order, with timestamps and a direct next action. **Done when:** parents can answer “what needs my attention?” without opening several pages.

41. **Make sibling switching unmistakable and safe.** Show the selected child’s name/photo/class on every child-specific page and clear stale child context after switching. **Done when:** direct-link and sibling-switch tests never show one child’s details under another child’s name.

42. **Fix mobile safe-area and header collisions.** Keep SkoolMate’s search, status, notifications, profile, and menu controls below the phone status bar and tappable at supported widths. **Done when:** the provided phone screenshot’s top icons are accessible on iOS/Android and at zoomed text sizes.

43. **Prevent floating controls from covering work.** Coordinate Owly, bottom navigation, assistant badges, modal buttons, and sticky actions around device safe areas and the keyboard. **Done when:** no primary action or form field is obscured on 320–430px screens.

44. **Make Owly’s welcome prompt useful and non-repeating.** Show a friendly, readable first-visit prompt with a clear ask/open/dismiss action, auto-dismiss after a short idle period, and respect dismissal across logins. **Done when:** Owly speaks from its own corner and does not repeatedly interrupt returning users.

45. **Replace the tiny quick tour with accessible guidance.** Readable 18px tour copy, skip/close behavior, and explicit replay are implemented; the dashboard action step now uses the signed-in user's primary role, with fallback guidance. Focused role-copy tests and a Playwright role-copy assertion added. **Still open:** verify keyboard/screen-reader behavior and complete a teacher phone usability check before marking done.

## P2 — Dashboard, debugging, and operational confidence

46. **Stop the old dashboard-card flash.** Gate legacy dashboard markup until the selected role’s current dashboard data and layout are ready; use a matching skeleton during load. **Done when:** repeat launches never flash the obsolete card layout from the supplied screenshot.

47. **Make setup progress reflect the real school.** Derive checklist steps from verified school records and allow authorised review/waiver of already-complete items; never treat a seeded count as a missing setup step. **Done when:** a school with existing staff/classes does not get told to create them again.

48. **Repair and stabilize the E2E demo environment.** Recent full E2E execution failed attendance selector checks and demo sign-out user-menu checks; investigate demo seeding, route timing, and selectors independently. **Done when:** authenticated attendance and sign-out workflows pass repeatedly without changing production access rules to satisfy stale tests.

49. **Add actionable error and delivery diagnostics.** Standardise request IDs, useful server-side errors, safe user messages, and delivery/retry status for sync, SMS, exports, and report generation. **Done when:** support can identify the failed operation and next action without exposing learner data or secrets.

50. **Run a measured pilot with real school roles.** Observe a teacher, headteacher, bursar, and parent using attendance, timetable, reports, fees, and offline sync; record task time, errors, and user-reported blockers. **Done when:** each pilot issue has an owner, severity, reproduction, and verified resolution before broad rollout.

## Suggested execution order

1. Complete the registration agreement rollout, privacy request workflow, and provider/retention evidence (1–5, 8).
2. Stabilise startup, offline queue safety, and school/account isolation (12–20).
3. Make calendar audience and timetable scheduling reliable (21–30).
4. Finish report configuration, completeness, calculation parity, and print workflow (31–38).
5. Improve parent/mobile/Owly and first-run dashboard experience (39–47).
6. Close the debugging and pilot loop before wider deployment (48–50).

## Evidence used

- Recent walkthrough issues reported by the school: wrong setup checklist despite existing records; old dashboard flash; PWA returning through home/login before dashboard; inaccessible phone header controls; Owly tour too small/repeating; whole-school event audience default; timetable not matching/importing school sheets; report-card settings and output formats needing flexibility; offline mode not dependable; parent portal needs UX refresh.
- docs/audit/2026-10-15-ground-usability.md: financial retry/reconciliation, attendance sync, report accuracy, parent switching, SMS delivery, timetable clashes, and field usability remain open or partial.
- docs/audit/2026-10-15-offline-speed.md: offline support is partial; first-time offline launch, cached class data, sync conflicts, school isolation, and low-end Android performance need verification.
- docs/ROADMAP.md: earlier technical risks include transactional registration, tenant checks, rate limits, API timeouts, report/fee consistency, and production-safe route handling. Re-check each item against current code before implementation; this list does not assume the older roadmap is still fully current.
- Current E2E run during this task: the full local suite completed with 151 passed, 42 failed, 3 skipped, and 13 not run. Most failures were authenticated workflows expecting seeded Supabase data while the isolated server had only the mock client; other failures include stale selectors/flows and a real fee-draft modal viewport defect. Focused auth/attendance flows passed separately.
